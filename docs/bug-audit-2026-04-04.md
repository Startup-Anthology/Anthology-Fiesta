# Fiesta CRM Bug Audit — 2026-04-04

**Product:** Fiesta CRM (Expo React Native + Node/Express API)
**Auditor:** Claude Code (4 parallel agents — API server, mobile app, integrations, database/schema)
**Scope:** Full monorepo — `artifacts/api-server`, `artifacts/mobile`, `lib/db`, `lib/api-zod`
**Total findings:** 49 bugs — 6 Critical, 15 High, 17 Medium, 11 Low

---

## Critical

---

### C-1 — Cross-user AI Insight Dismiss (IDOR / authorization bypass)

**Area:** API server
**File:** `artifacts/api-server/src/routes/ai.ts` ~line 232

`PATCH /ai/insights/:id/dismiss` updates the row using only `insightId`, with no `userId` filter. Any authenticated user can dismiss another user's insight cards.

```ts
// Current (vulnerable)
where(eq(aiInsightsTable.id, insightId));

// Fix
where(
  and(eq(aiInsightsTable.id, insightId), eq(aiInsightsTable.userId, userId)),
);
```

**Fix:** Add `userId` to the WHERE clause, matching the `findOwned()` pattern used everywhere else.

---

### C-2 — Lead email uniqueness not enforced at DB level

**Area:** Database schema
**File:** `lib/db/src/schema/leads.ts`

`leadsTable` has no unique constraint on `(userId, email)`, even though `contactsTable` has one. This allows duplicate email addresses for the same user — breaking Notion sync (email-based fallback matching), Gmail webhook routing, and reporting.

**Fix:** Add `.unique()` on `(userId, email)` in the Drizzle schema, then run `drizzle-kit push`.

---

### C-3 — Expired sessions never purged (unbounded table growth)

**Area:** Database / auth
**File:** `lib/db/src/schema/auth.ts`, `artifacts/api-server/src/lib/auth.ts`

`sessionsTable` has an `expire` column, and `getSession()` deletes a session on-demand if it's expired, but there is no background job to bulk-delete stale rows. Sessions accumulate forever, degrading query performance over time.

**Fix:** Add a nightly cleanup job (runs once per day via `setInterval`) in the startup sequence:

```sql
DELETE FROM sessions WHERE expire < now()
```

---

### C-4 — Unhandled promise rejection in profile save (silent failure)

**Area:** Mobile app
**File:** `artifacts/mobile/app/settings/profile.tsx` ~line 48

The mutation's `onSuccess` handler calls `await refreshUser()` after storing the new token. If `refreshUser()` throws (network error, 401), the error propagates uncaught — the mutation's `onError` is never called. The success alert fires before the async call resolves, so the user sees "Saved" even when the refresh silently failed.

**Fix:** Wrap `refreshUser()` in try-catch inside `onSuccess`, or move it into the mutation itself so `onError` handles failures.

---

### C-5 — Non-null assertion on templateId in sequence step add

**Area:** Mobile app
**File:** `artifacts/mobile/app/sequence/[id].tsx` ~line 69

```ts
mutationFn: () => api.addSequenceStep(Number(id), templateId!);
```

`templateId!` bypasses TypeScript's null check, but `templateId` is never validated before the mutation fires. If the user taps "Add Step" without selecting a template, `undefined` is sent to the API, producing an unhelpful 400 with no UI feedback.

**Fix:** Disable the "Add Step" button when `!templateId`, or add a guard clause at the top of `mutationFn`.

---

### C-6 — Broadcast recipient query error shows blank screen

**Area:** Mobile app
**File:** `artifacts/mobile/app/broadcast/new.tsx` ~line 119

`recipientsQuery` has no `isError` handling. When it fails (API error, timeout), `isLoading` becomes false and `data` is `undefined`, rendering an empty list with no message. The user cannot tell whether zero contacts matched or the query failed.

**Fix:** Render an explicit error state when `recipientsQuery.isError` is true, with a Retry button that calls `recipientsQuery.refetch()`.

## High

---

### H-1 — No timeout on OpenAI streaming calls

**Area:** API server
**File:** `artifacts/api-server/src/lib/ai/orchestrator.ts` ~lines 151–216

`processChat()` opens SSE streaming to OpenAI without any timeout. If OpenAI hangs, the HTTP connection never closes, consuming a server thread indefinitely. Under load, this exhausts the connection pool.

**Fix:** Wrap streaming calls with `AbortController` + `setTimeout(30000)`. Write a timeout error event to the SSE stream before closing.

---

### H-2 — Worker startup failures are silently swallowed

**Area:** API server
**File:** `artifacts/api-server/src/index.ts` ~lines 55–60

The six `start*Worker()` calls have no try-catch. If any worker fails to initialize (DB connection issue, missing config), the server continues without logging the failure. Workers appear started but are not running.

**Fix:** Wrap each worker start in `try { start*Worker() } catch (e) { console.error('[worker] Failed to start:', e) }`.

---

### H-3 — JSON.parse crash in insight worker can kill the run

**Area:** API server
**File:** `artifacts/api-server/src/lib/ai/insightWorker.ts` ~line 215

`frameInsightsWithAgent()` calls `JSON.parse()` on the raw OpenAI response. If the model returns malformed JSON (common with streaming truncation), the parse throws. The outer try-catch in `generateInsightsForUser()` catches it, but the error context (raw response) is not logged, making debugging impossible.

**Fix:** Log the raw response string before `JSON.parse()`. Wrap in try-catch with a fallback to an empty insights array rather than throwing.

---

### H-4 — OAuth token refresh race condition

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/registry.ts` ~lines 40–60

`getFreshTokens()` has no in-flight deduplication. Two concurrent requests for the same user+provider can both detect token expiry and both call `refreshAccessToken()` simultaneously. This burns two refresh token grants — if the OAuth provider invalidates the first refresh token on use, the second call fails with `invalid_grant`, breaking the integration until the user reconnects.

**Fix:** Maintain a `Map<string, Promise>` of in-flight refresh operations, keyed by `userId:provider`. If a refresh is already in flight, await the existing promise instead of starting a new one.

---

### H-5 — Token decryption crash on corrupted data

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/tokenManager.ts` ~lines 70–90

`decryptToken()` uses `crypto.createDecipheriv()` + `.final()` without try-catch. If the stored token is corrupted (wrong encryption key rotation, partial write), `decipher.final()` throws synchronously, crashing the request handler with an unhandled exception.

**Fix:** Wrap the decryption block in try-catch. On failure, return `null` and mark the integration as requiring re-auth rather than crashing the request.

---

### H-6 — Audit log table missing foreign key on userId

**Area:** Database schema
**File:** `lib/db/src/schema/auditLog.ts`

`auditLogTable.userId` has an index but no foreign key constraint. If a user account is deleted, all their audit records become orphaned with an invalid `userId` reference — no cascade delete fires.

**Fix:** Add `.references(() => usersTable.id, { onDelete: 'cascade' })` to the `userId` column.

---

### H-7 — Email not normalized in leads/contacts routes

**Area:** Database / API
**File:** `artifacts/api-server/src/routes/leads.ts` ~line 32, `contacts.ts` ~line 43

`POST /auth/register` applies `.trim().toLowerCase()` to emails, but the leads and contacts create/update routes do not. `john@example.com` and `John@Example.com` are stored as separate entries, breaking Notion sync email-matching, Gmail webhook routing, and duplicate detection.

**Fix:** Add `.trim().toLowerCase()` to the email field in `createLeadSchema` / `createContactSchema` Zod validators, or normalize in the route handler before DB insert.

---

### H-8 — Broadcast template cascade delete leaves orphaned broadcasts

**Area:** Database schema
**File:** `lib/db/src/schema/broadcasts.ts` line 8

`broadcastsTable.templateId` uses `onDelete: 'set null'`. When a template is deleted, all its broadcasts have `templateId = null`. Attempting to view or resend those broadcasts fails silently or renders incorrectly when the UI assumes `templateId` is always set.

**Fix:** Change to `onDelete: 'cascade'` to delete orphaned broadcasts, or add explicit null-handling in all broadcast views.

---

### H-9 — Broadcast recipients not deduplicated before send

**Area:** API
**File:** `artifacts/api-server/src/lib/validation.ts` ~lines 135–143

`createBroadcastSchema` validates that segment arrays are non-empty, but does not deduplicate. A recipient matching multiple segment criteria (e.g., a lead that is both "active" and "beta") will receive the same email twice.

**Fix:** After expanding segments to recipient lists in the route handler, deduplicate by `(leadId | contactId)` before enqueuing sends.

---

### H-10 — Search screen snapshot lock not released on unmount

**Area:** Mobile app
**File:** `artifacts/mobile/app/search.tsx` ~lines 40–60

The `isSearching` snapshot lock is released when the user clears the input, but not when the component unmounts (user navigates away mid-search). Stale lock state can persist and affect the next visit to the screen.

**Fix:** Add a `useEffect` cleanup: `return () => setIsSearching(false)`.

---

### H-11 — Activity Detail Modal save button stays disabled after error

**Area:** Mobile app
**File:** `artifacts/mobile/components/ActivityDetailModal.tsx` ~line 194

The save button is disabled while the mutation is pending (`disabled={isSaving}`). When the mutation fails, `isSaving` is never reset because no `onError` handler exists. The user cannot retry without closing and reopening the modal.

**Fix:** Add `onError: () => setIsSaving(false)` (or equivalent) to the mutation, and show an error message so the user knows to retry.

---

### H-12 — Missing null check on activity type in ActivityDetailModal

**Area:** Mobile app
**File:** `artifacts/mobile/components/ActivityDetailModal.tsx` ~line 100

`TYPE_COLORS[activity.type]` crashes if `activity.type` is null or empty (possible if the server returns malformed data or DB has no enum constraint — see M-8). The badge renders silently with fallback color but the chip selector in edit mode fails to highlight any chip.

**Fix:** Default to `'other'`: `const typeColor = TYPE_COLORS[activity.type || 'other'] || colors.textTertiary`.

### H-13 — Profile token refresh race condition on slow devices

**Area:** Mobile app
**File:** `artifacts/mobile/app/settings/profile.tsx` ~lines 43–48

`SecureStore.setItemAsync()` is called, then immediately `refreshUser()` reads from SecureStore. On slow devices or concurrent sessions, `refreshUser()` may read a stale token if the write hasn't committed to the secure keychain yet.

**Fix:** Await `SecureStore.setItemAsync()` confirmation before calling `refreshUser()`, or pass the new token directly to `refreshUser(newToken)`.

### H-14 — Broadcast wizard shows blank on segment/template load failure

**Area:** Mobile app
**File:** `artifacts/mobile/app/broadcast/new.tsx` ~lines 130–140

`segmentQuery.isError` and `templatesQuery.isError` are not handled. On failure, the user sees empty dropdowns with no error message and no way to retry.

**Fix:** Render `<ErrorState>` + Retry button when either query has `isError: true`.

### H-15 — Merge tag typos in templates silently produce broken emails

**Area:** Mobile app
**File:** `artifacts/mobile/app/template/[id].tsx` ~lines 121–125

The template editor lists 9 valid merge tags but does not validate them on save. A typo like `{{first_nam}}` passes through to the email renderer, which skips it silently — the recipient sees a blank field. No preview is available.

**Fix:** Before saving, regex-match all `{{...}}` patterns and warn if any are not in the allowed list. Consider adding a preview button that renders the template with sample data.

## Medium

### M-1 — Drip advisory lock not released on worker crash mid-enrollment

**Area:** API server
**File:** `artifacts/api-server/src/lib/dripWorker.ts` ~lines 103–267

If an unhandled error occurs after `tryLockEnrollment()` succeeds but before `unlockEnrollment()` is called, the enrollment remains locked for up to 5 minutes (stale lock timeout). The 5-minute recovery is acceptable but the failure mode is not visible in logs.

**Fix:** Wrap the per-enrollment processing block in `try-finally { await unlockEnrollment(enrollmentId) }` to guarantee release on any error path.

---

### M-2 — `isBeta` query parameter not validated in leads route

**Area:** API server
**File:** `artifacts/api-server/src/routes/leads.ts` ~lines 17–21

`GET /leads?isBeta=invalid` silently falls through the condition check without erroring or warning. The filter is not applied and results are confusingly unfiltered.

**Fix:** Validate `isBeta` against `z.enum(['true', 'false']).optional()` using a Zod query schema.

### M-3 — Notion push sync errors silently swallowed

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/notionSync.ts` ~lines 15–35

`fireAndForgetLeadSync()`, `fireAndForgetContactSync()`, `fireAndForgetActivitySync()` call `Promise.all()` without `.catch()`. API errors (rate limits, invalid database ID, permission denied) are lost. Users have no signal that Notion sync is broken.

**Fix:** Add `.catch((err) => { console.error('[notion-sync]', err); logAudit(...) })` to each Promise.all() call. Consider setting an integration error flag visible in the UI.

### M-4 — SA pull sync crashes when only webhook is configured

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/saSync.ts` ~lines 26–39

`isSAConfigured()` returns `true` when only `SA_WEBHOOK_SECRET` is set (webhook-only mode). But `POST /api/sa/sync` calls `getSAConfig()` which throws if `SA_CRM_API_KEY` / `SA_BASE_URL` are missing. A user in webhook-only mode triggering manual sync gets a 500 with a confusing error.

**Fix:** Guard `fetchSAContacts()` with a separate `isPullSyncConfigured()` check. Return a clear 400: "Pull sync not configured; using webhook-only mode."

### M-5 — Gmail webhook audience env var missing produces cryptic 401

**Area:** Integrations
**File:** `artifacts/api-server/src/routes/gmailWebhook.ts` ~lines 50–75

Behavior is intentional (fails closed), but when neither `GMAIL_WEBHOOK_AUDIENCE` nor `API_BASE_URL` is set, the 401 response has no explanation. Debugging this requires reading source code.

**Fix:** Log a clear warning at startup: `"Gmail webhook: GMAIL_WEBHOOK_AUDIENCE not set — webhook will return 401"`. Optionally return a 503 with a helpful message instead of a bare 401.

### M-6 — No timeout on OAuth token refresh HTTP calls

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/oauth.ts` ~lines 90–130

`refreshAccessToken()` makes external HTTP calls with no timeout. If Google/Microsoft OAuth endpoints are slow, the entire user request hangs for up to Node's socket timeout (~2 minutes).

**Fix:** Use `AbortController` with a 10-second timeout, or `Promise.race()` against a timeout rejection. Propagate a `TokenRefreshTimeoutError` so callers can mark the integration as errored.

### M-7 — Notion sync not atomic; concurrent updates can create duplicates

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/notes/notion.ts` ~lines 50–80

`syncLead()` and `syncContact()` do a read-then-write pattern (fetch by `notionPageId`, then create or update). Two concurrent requests for the same lead can both read "no existing page" and both create, producing duplicate Notion pages.

**Fix:** Use Notion's filter query to atomically check-or-create. Add a `notionPageId` uniqueness check before creating. Implement a per-userId per-entity in-memory lock to serialize Notion syncs.

### M-8 — Horizon/SA sync blindly overwrites user edits

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/horizonSync.ts` ~lines 50–80`,`saSync.ts` ~lines 126–140

Both upsert functions match on email and overwrite local fields with no timestamp check. If a user edits a lead in Fiesta after the last pull, the next sync silently reverts their changes to the external system's version.

**Fix:** Compare `updatedAt` timestamps. Only update local record if the incoming `updatedAt` is newer. If no external timestamp is available, add a `lastSyncAt` field and skip within a grace period.

### M-9 — Drip step template reference has no cascade constraint

**Area:** Database schema
**File:** `lib/db/src/schema/dripSequences.ts` ~lines 21–35

`dripSequenceStepsTable.templateId` has no FK constraint or cascade rule. Deleting an email template leaves drip steps pointing at a nonexistent template, causing errors when the drip worker tries to render the email.

**Fix:** Add `.references(() => emailTemplatesTable.id, { onDelete: 'cascade' })` to `templateId` — deleting a template deletes its steps.

### M-10 — Activity type is a free-form string with no enum constraint

**Area:** Database schema
**File:** `lib/db/src/schema/activities.ts`

`activities.type` is `varchar(255)` with no check constraint. Typos (e.g., `"emai_sent"`) can be inserted, breaking AI insights heuristics, Slack notifications, and UI icons that branch on type strings.

**Fix:** Define a Drizzle `pgEnum` for activity types and apply it to the column. Add a Zod enum to the Zod validation schema.

### M-11 — Trigger rules have no cycle detection

**Area:** Database / API
**File:** `lib/db/src/schema/triggerRules.ts`, `artifacts/api-server/src/routes/leads.ts` ~lines 102–113

The status-change handler iterates trigger rules and enrolls leads in sequences without checking for circular chains (Rule A → Sequence X → triggers Rule B → re-enrolls in Sequence X). This can produce infinite enrollment loops.

**Fix:** Track `processedTriggerIds` in the current request. Skip any trigger already processed. Apply a max-depth guard (e.g., 5 levels).

### L-1 — Outlook calendar event times not validated before API call

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/calendar/outlook.ts` ~lines 40–70

`createEvent()` / `updateEvent()` do not validate that `startTime < endTime`. Outlook rejects these with a 400, which is silently caught and logged — no error is surfaced to the user.

### L-2 — Gmail attachment size not validated before send

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/email/gmail.ts` ~lines 60–68

Attachments are base64-encoded without a size check. Gmail rejects messages over 25 MB (base64 inflates ~33%), returning a cryptic API error.

**Fix:** Sum attachment sizes before encoding. Throw `AttachmentTooLargeError` if total > ~18 MB raw (25 MB base64 limit with headroom).

### L-3 — Integration error state not cleared after successful token refresh

**Area:** Integrations
**File:** `artifacts/api-server/src/lib/integrations/registry.ts` ~lines 55–70

When a token refresh succeeds, the new tokens are stored but any existing integration error flag is not cleared. An integration that was temporarily broken (e.g., network glitch) stays showing as errored in the UI even after recovery.

**Fix:** After a successful refresh, call a `markIntegrationSuccess()` to clear the error state in the `integrations` table.

1. **C-1** — Ship today: IDOR on insight dismiss is a security bug exploitable by any logged-in user

4. **C-4/H-11** — Mobile error handling on auth + activity modal: user-facing silent failures
5. **M-11** — Trigger cycle detection before enabling automation features
6. **C-3/M-1** — Session cleanup + drip lock release: operational hygiene for long-running prod
